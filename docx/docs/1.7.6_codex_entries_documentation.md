## Purpose

**Owns:** every write to codex resources — ID generation, format validation, section placement, topic/category creation, list sync, and all write guards.
**Does not own:** what gets written (the model's judgement via 1.7.5).
**Depends on:** 1.7.2 (store), 1.7.7 (compat), 1.7.1 (read tracker). **Dependents:** the model (tool surface).

## Public API & contracts

- `codex_add_entry(topic, category?, entries[])` — batches; generates the 6-char `[ID]`; strips wrapper noise; validates per-kind format (rule/gotcha one line; issue = symptom+cause+fix with auto `(YYYY-MM)`); one bad entry fails the batch labelled `entries[i]`; appends at the end of the canonical section; creates topic skeletons + category folders; runs the list sync internally on topic creation.
- `codex_edit_entry(topic, id, kind?, text?, cause?, fix?)` — keeps the ID; kind change moves section; issue dates refresh; unknown ID lists the IDs present.
- `codex_remove_entry(topic, id)` — deletes all entry lines; never the topic file or the list.

## Internal architecture & data flow

Guards in order: version compat (1.7.7) -> read-before-write for existing topics (1.7.1's tracker) -> refused top-level docs -> per-kind format -> **generality + secrets guard** (`guardGeneral`: rejects real absolute machine paths, real URLs, the current project's directory name — placeholder shorthand like `/path/to/x`, `example.com`, `<token>` passes — and credential-looking content: concrete `KEY=value` assignments, JWTs, bearer literals, private-key blocks; the error tells the caller to reword generically / drop the secret) -> exact-duplicate backstop (normalized lead match). Writes are atomic (tmp + rename) and serialised via `withFileMutationQueue(absPath)`.
