## Purpose

**Owns:** the extension contract — `ExtensionAPI` (events, `registerTool`, `registerCommand`, `registerShortcut`, `appendEntry`, renderers), `ExtensionContext` / `ExtensionCommandContext`, the TUI component model (`pi-tui`), AI utilities (`pi-ai`, eg `StringEnum`), and `typebox` schemas.
**Does not own:** any toolset feature logic (all of branch 1).
**Depends on:** nothing in the project. **Dependents:** every module in branch 1 depends on it by ID.

## Public API & contracts

Peer dependencies (package.json): `@earendil-works/pi-coding-agent`, `@earendil-works/pi-ai`, `@earendil-works/pi-tui`, `typebox` — all `*`. Key surfaces used:

- Lifecycle events: `session_start` (with `reason`), `before_agent_start`, `context`, `tool_call`, `tool_result`, `message_end`, `agent_settled`, `session_shutdown`, `model_select`.
- Tools: `pi.registerTool({ name, label, description, promptSnippet, promptGuidelines, parameters, execute })`; errors are thrown from `execute`.
- Commands: `pi.registerCommand(name, { description, handler(args, ctx) })`; command ctx adds `waitForIdle()`, `switchSession()`.
- UI: `ctx.ui.notify/select/confirm/custom`, `setWidget`, `setStatus`; entry/message renderers.
- State: `pi.appendEntry(customType, data)` (durable, not in LLM context) vs `pi.sendMessage` (in context).
- File-mutating tools wrap in `withFileMutationQueue(absPath)`; tool output truncated via `truncateHead`/`truncateTail`.

## Internal architecture & data flow

pi loads `extensions/aftc-toolset/index.ts` through **jiti** — raw TypeScript, no compile step, no `dist/`. Modules stay alive across `/new` (the factory does not re-run), which is why config must never be cached in module memory (1.2). Print mode (`pi -p`) disposes the runtime as soon as the CLI prompt resolves — extension commands that inject a follow-up turn must hold the command open (`ctx.waitForIdle()`), see 1.8.1.

## Configuration

No project-side configuration. pi is configured by the user (settings.json, keybindings.json); the toolset never writes pi config.

## Setup, seeding & first run

`pi install npm:pi-aftc-toolset`, then `/aftc-install` (runtime deps) and `/reload`. pi discovers the package via its `pi` manifest (`extensions/`, `skills/`, `themes/`).

## Testing

`tests/help-registry-check` loads every command-registering module through pi's bundled jiti with a mock `ExtensionAPI` — the canonical harness pattern. Local jiti probes outside pi need `NODE_PATH` pointing at pi's nested `node_modules` (pi-tui/pi-ai are nested under pi-coding-agent).

## Operational notes & known limitations

- jiti does not type-check: interface drift surfaces as runtime `undefined`, not compile errors.
- pi APIs used are documented in `docs/extensions.md` of the installed pi package; the maintained gotchas live in the codex `tools/pi-extension.md` resource.
- Version skew: the toolset tracks pi's current API (eg `agent_settled`, `reason` fields); older pi versions may lack them.
