## Purpose

**Owns:** per-feature unit/integration checks runnable on any dev machine in seconds.
**Does not own:** containerised gates (5.2).
**Depends on:** jiti harness (5). **Dependents:** none.

## Public API & contracts

Run: `node tests/<suite>/<suite>.mjs` — exit 0/1, `passed/failed` summary. Notable suites:

- `help-registry-check` — every `registerCommand` has a help entry and vice versa (both directions).
- `config-fresh-read-check` — the no-config-cache regression.
- `codex-*` suites — entries (73 checks incl. generality/secrets guard), compat, detect, status, integration (3 files), lifecycle.
- `docx/docx-check.mjs` — 87 checks: backup rules, scripts, command end-to-end, repo-copy fixtures (`docx_test_01`–`07`, `test_project`).
- `ssh-*` — module, carrier lifecycle, redaction, forms, overlays, VT100 screen.
- Footer/usage: `footer-widget-check`, `footer-task-time-check`, `footer-timeframe-check`, `allowance-check`, `usage-report-check`.
- Feature suites: `keys-check`, `notify-check`, `intros-check`, `quick-open-dir-check`, `run-script-check`, `qwencloud-check`, `bulk-read-check`, `install-*`, `npm-package-check`, `data-migration-check`, `aftc-ui-check`.

## Internal architecture & data flow

Mock `ExtensionAPI` captures registered tools/commands/handlers; handlers are fired with fabricated events; asserts are explicit (`check(name, cond)` pattern). Fixtures are created fresh per run (temp dirs or the suite's own folder, cleaned/recreated).

## Configuration

Per-suite env overrides where needed (`PI_CODING_AGENT_PATH`, `AFTC_TOOLSET_DATA_ROOT`).

## Setup, seeding & first run

Nothing beyond the repo checkout (+ `npm install` for suites touching better-sqlite3/adm-zip).

## Testing

The suites are the tests.

## Operational notes & known limitations

- A suite that only exercises code without asserting outcomes is pruned, not kept (tests/readme.md philosophy).
