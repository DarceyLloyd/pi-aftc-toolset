# 1.8 - docx Generator

The `/docx` project documentation generator: backs up existing docs, injects the guide's execution prompt, and lets the model regenerate the full documentation set.

## Purpose

**Owns:** the `/docx` feature end-to-end — confirmations, backup, prompt assembly, and the scripts the model runs mid-generation.
**Does not own:** the generated output (belongs to the user's project).
**Depends on:** 1.1, 1.3, adm-zip (zip script). **Dependents:** none.

## Public API & contracts

`/docx [--yes]`. `--yes` skips both modals (headless). Help-registry category General.

## Internal architecture & data flow

Flow: context-window gate (`ctx.getContextUsage().percent >= 10` → warn modal) → main confirm modal (backup warning) → deterministic backup (1.8.2) → execution prompt extracted from the shipped guide's section 18 and injected via `pi.sendUserMessage` with `[PROJECT_PATH]`/script paths substituted. In print/headless mode the command holds itself open (poll for turn start, then `ctx.waitForIdle()`) because `sendUserMessage` is fire-and-forget and print mode exits when the command returns. The model generates the docs, then runs the shipped scripts: map-scan (step 1), link-audit (step 11, loops until PASS), zip-old (final action: `docx/old_docs/` → `docx/old_docs.zip`, folder removed).

## Configuration

None (a slash command is opt-in by nature).

## Setup, seeding & first run

Nothing; adm-zip arrives via `/aftc-install` (npm install).

## Testing

`tests/docx/docx-check.mjs` (87 checks: backup rules, re-run fold-in, first-run, leftovers, link-audit pass/fail, zip-old, repo-copy run, command end-to-end with mock pi) and `tests/docx/docx-e2e-linux.mjs` (live container run against a repo copy).

## Operational notes & known limitations

- Destructive-adjacent by design: old docs end up zipped; the modal tells the user to make their own backup first.
- Backup scope is a whitelist (root + `./docs/` + previous `docx/`), so framework/sub-project docs are structurally unreachable.
