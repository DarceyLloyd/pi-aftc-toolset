## Function

Implements the `TurnRecorder` interface (types.ts) that core.ts (1.4.1)
calls on every assistant `message_end` and every settled task: writes one
metrics row per turn into the shared SQLite DB (1.2 `db.ts`). No commands,
no UI. Source: `usage-recording.ts` (249 lines). Does not import core.ts or
usage-report.ts.

## What is recorded

Per-turn METRICS and prompt-type CLASSIFICATION FLAGS only — never prompt
or response text, file paths, tool names/arguments or thinking content
(those live in pi's session JSONL). ~100 bytes per row.

Columns written per turn row (27 total): `turn, timestamp, session_id,
prompt_index, model_name, thinking_level, thinking_ms, response_ms,
cost_usd, input_tokens, output_tokens, cache_read, cache_write,
context_window, context_tokens` + flags `user_prompt, base_prompt,
sub_prompt, steering_prompt, followup_prompt, continuation_prompt` +
`prompt_kind` ("base" | "continuation" | "steer" | "followup" |
"auto") + `device_id` (one UUID per data dir tagging this machine's
rows with this installation's owner id; '' = legacy) + v1.21.x
`provider` (deepseek, qwencloud, kimi-coding, ...), `tool_calls`,
`response_chars`, `prompt_chars` (per-turn size metrics). `context_window` /
`context_tokens` (v1.21.x) hold the model's
declared context window and pi's `getContextUsage()` estimate at
`message_end`.

Task rows (via `recordTask` from core's `agent_settled`, 19 columns):
`session_id, prompt_index, timestamp, task_ms, stop_reason
('complete'|'error'|'aborted'|'toolUse'), model_name, thinking_level,
turn_count` + v1.21.x context (`context_window`,
`context_start_tokens`, `context_end_tokens` — pi's context estimate at
task start / end) and allowance snapshots (`allow_provider`,
`allow_5h_start/end`, `allow_weekly_start/end` — provider-reported 5h /
weekly used-%, captured by core.ts at agent_start / agent_settled;
NULL when the provider reports no allowance) + `device_id` +
`allowance_reported` (1 when the active provider reported an allowance
window — footer line-5 availability; subscription plans only) +
`provider` (provider id that ran the task).

Error rows (new v1.21.x `errors` table, via `recordError` from core's
failing `message_end` — `stopReason === "error"`): `session_id,
prompt_index, timestamp, model_name, thinking_level, error_type,
error_message, device_id, provider, error_code`. `error_type` is
classified by core.ts's `classifyError()`: `rate-limit` (429) /
`allowance` (quota / usage limit) / `context` (context window / token
limit) / `overloaded` (5xx) / `not-found` (404) / `auth` (401-403) /
`timeout` (408) / `aborted` (transport abort) / `network` / `other`.
`error_code` is the HTTP status code when the message carries one
(NULL otherwise). User aborts (`stopReason === "aborted"`) are NOT
errors — they are counted from the tasks table.

Tool error rows (new `tool_errors` table, via `recordToolError` from
core's `tool_result` hook — a tool call whose result carried `isError`):
`session_id, prompt_index, timestamp, model_name, thinking_level,
provider, tool_name, error_kind, error_message, error_signature,
device_id`. `error_kind` is classified by core.ts's `classifyToolError()`:
`invalid-args` / `stale-anchor` / `not-found` / `bad-regex` / `permission` /
`timeout` / `network` / `missing-binary` / `other`. `error_signature` is a
normalised copy of the message (lowercase, whitespace collapsed, digits
and paths replaced with placeholders) so the report can collapse repeated
identical mistakes into one row with a repeat count. Tool errors are a
model-misuse signal (wrong args, stale anchors, bad regex), distinct from
the provider failures in the `errors` table — both feed the Errors tab
(1.4.5), with provider errors first.

## Recording policy

- Zero-cost turns (free models / $0 subscription turns) ARE recorded —
  their counts/timings are useful; the report keeps them out of COST
  averages with paid-only denominators. `RECORD_ZERO_COST_TURNS` (module
  constant) can skip them entirely.
- Negative-cost turns are never recorded (defensive).
- The in-memory footer accumulator always updates regardless, so the live
  footer shows the real last-turn cost.
- All recording is LOCAL ONLY: turns/tasks/errors/tool_errors are always inserted
  into the SQLite turns.db — usage data never leaves the machine.

## Runtime states

- DB unavailable (better-sqlite3 missing): `recordTurn`/`recordTask`/
  `recordError` are no-ops; footer still works; `/aftc-install` fixes
  (1.5.3).
- Old DB (pre-v1.21.x): db.ts migrations add the new columns in place
  on the first open; old rows keep defaults (context 0, allowance
  NULL) and the report falls back / shows N/A.
