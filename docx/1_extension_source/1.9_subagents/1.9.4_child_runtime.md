The worker extension loaded INSIDE each child (`--no-extensions` +
explicit `-e`). Lives in the CODE TREE — never in the shipped data
seed (design correction #2).

- Run config via `AFTC_SUBAGENT_RUN_CONFIG` (private 0600 JSON written
  by the supervisor): `{ runId, operative, codexReadEnabled,
  codexWriteEnabled, codexTopics, codexRoot? }`. Missing/corrupt
  config degrades gracefully (protocol without codex; never crash).
- `before_agent_start` prepends the fixed worker protocol to the
  system prompt (byte-stable within a run — static text + config
  values only; the system prompt is the cached prefix). Protocol:
  fresh-context notice, do-the-task-yourself, final text IS the
  report, prefer `report_result`, blocked => report blocked (no UI).
- `report_result` tool (design 5.4): summary (16 KiB cap),
  status completed|blocked, questions (max 4), artifacts (max 8),
  terminate. FIRST report wins per child process (== per run);
  duplicates acknowledged + discarded (invariant 2). Batch-scoped
  `terminate` is enforced by the SUPERVISOR (it waits for the
  turn_end that closes the batch).
- Capability Exposure (design 11): when the gate resolved on
  (parent codex enabled AND `codexAccessEnabled` AND profile `codex`),
  registers a read-only `codex_load` against the LIVE store (searches
  all category folders - flat and nested - plus root-level topics and
  top-level files, 48 KiB cap) and puts a
  bounded brief (tool contract + topic list) in the prompt.
  `codex_write` is parsed but v1 stays read-only (documented).
  Nothing else of the toolset exists in a child.

## Child states

Children are hermetic: launched `--no-extensions` + explicit `-e`, so
nothing else of the toolset exists inside a child. Codex access is
triple-gated and read-only in v1 (`codex_write` is parsed but inert);
without the run-init payload the runtime idles as a plain RPC peer.
