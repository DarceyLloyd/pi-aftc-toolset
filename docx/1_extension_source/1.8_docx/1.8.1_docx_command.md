## Function

The two commands and their shared handler (`handleDocxRun`, mode
`generate` | `update` selected by the `DOCX_MODES` table). Source:
`docx/docx.ts` (579 lines). Project root = `ctx.cwd`. Args (both):
`--yes` (skip confirmations; headless), `--type <key>` / `--type=<key>`
(headless type selection).

- `/docx` — full regeneration (guide section 18, zip label `original`).
- `/docx-update` — drift reconciliation of an EXISTING doc set (guide
  section 22, zip label `update`).

## Flow (exact order, both commands)

1. **Hard gate**: `ctx.getContextUsage().percent >= 25` → refuse. TUI:
   full-screen info MODAL "context window too full" explaining the
   compaction-corruption risk and the fix (/new, then the command).
   Headless: warn line. Applies EVEN WITH `--yes`.
2. **Update-mode gate** (`/docx-update` only): no `./docx/` at the
   project root → warn and refuse ("nothing to update — run /docx
   first"). No confirmations, no backup, no prompt.
3. **Existing-docx modal** (`/docx` only, TUI only): when `./docx/`
   already exists, a modal asks "An existing docx folder has been
   detected, would you like to:" — *Update your existing documentation*
   (the run switches to update mode and continues through the normal
   pipeline) or *Re-build your documentation fresh* (the generate flow
   continues). Esc cancels. Headless unchanged: `--yes` rebuilds;
   without `--yes` headless refuses and asks for `--yes`.
4. **Confirmations** (skipped by `--yes`; headless without `--yes` that
   needs confirmation is told to re-run with `--yes`):
   - Advisory at ≥20% usage: CONFIRM modal — usage is modest (measured
     5–8% of a 1M window, under 20% even for large projects) but the run
     is LONG; highly advises /new first ("Proceed anyway" / "Exit").
   - Backup confirmation MODAL (mode-specific wording): `/docx` warns all
     previous documentation is moved into ./docx/old_docs/ (zipped into
     ./docx/backups/ at the end) and advises making your own backup
     first; `/docx-update` explains the reconcile (new/removed/drifted
     docs, README fact-checked WITHOUT rewriting) and the backup zip.
     Both set the long-wait expectation.
5. **Project-type selection**: TUI picker MODAL (11 types, auto-detect
   pre-selected); headless: `--type`, else auto-detect, else refuse with
   the key list.
6. **Backup** (1.8.2) — any error aborts before the model is engaged.
7. **Prompt assembly & injection** (`buildDocxPrompt`): the mode's CORE
   execution prompt extracted from its guide section (the fenced ```text
   block — the guide is the single source of truth, never duplicated):
   section 18 "AI Execution Prompt" for `/docx`, section 22 "AI Update
   Execution Prompt" for `/docx-update`. The chosen pack is appended
   after `---`; `[PROJECT_PATH]` / `[GUIDE_PATH]` / `[MAP_SCAN_PATH]` /
   `[LINK_AUDIT_PATH]` / `[ZIP_OLD_PATH]` are substituted with
   forward-slash absolute paths and `[ZIP_OLD_LABEL]` with the mode's zip
   label (`original` | `update`). Prefixed with the mode banner ("You are
   running /docx" / "You are running /docx-update ... reconcile, never
   regenerate"), project-type line and BACKUP STATE summary (moved /
   copied / partner-skipped / docs-leftovers / first-run text). The whole
   guide is appended after the prompt. Injected as a user message — the
   model then does the work (the model also runs map-scan / link-audit
   mid-run and zip-old as the final action; `/docx-update`'s prompt runs
   diff plan -> mint -> retire -> correct -> cross-refs/link-audit ->
   README in place -> finalise).

## Auto-detect (`detectProjectType`)

Heuristic pre-select (the user confirms in the picker; headless without
`--type` it is the decider): probes root files (package.json, compose,
Dockerfiles, source extensions, …) in the DOCX_TYPES order. No match →
null (picker without pre-select; headless refuses).

## Runtime states

- First run (no previous docs): backup summary says so; steps referencing
  old docs are skipped by the model. (`/docx-update` never reaches this —
  it requires an existing `./docx/`.)
- `--yes` + ≥25% context: still refused (hard gate).
- Missing guide/pack file → prompt assembly returns null → error line.
- Headless print mode: the command holds open until the turn starts and
  the agent settles (otherwise pi exits and kills the run).

## Rules / invariants

- Exactly ONE type pack per run — the old all-in-one prompt is gone; the
  same pack injection serves both commands.
- The model never moves/zips docs itself (backup is tooling-owned; the
  final zip is `scripts/zip-old.mjs <root> <label>`).
- `/docx-update` never regenerates: docs are edited in place, retired IDs
  are marked reserved, and the root README is adjusted with minimal
  targeted edits only.
