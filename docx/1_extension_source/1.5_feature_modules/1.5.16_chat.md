## Function

Peer chat between two or more pi instances over ONE shared append-only text
file (`chat.log`). The extension owns ALL transport: a watcher detects new
records, filters them by the addressed name, and injects matching ones into
this pi instance as real user messages (`pi.sendUserMessage`) — the model
never polls, never parses the file and never spends tokens on transport.
Peer messages simply appear in the chat and the agent answers them; replies
are sent back automatically (or via `chat_send_message`). Source:
`chat.ts`.

## Identity & the entry gate

Every participant (AI or human) is a pi instance with a **name** and a
**role**; an AI cannot act in the chat (send / done / claim) until both are
set — the tools error with exactly what is missing. Multi-word names/roles
are supported (spaces survive sanitizing; the log protocol parses them
fine). **Name and role are per-process and live ONLY in this pi process's
environment (`AFTC_CHAT_NAME` / `AFTC_CHAT_ROLE`) — never config.json:**
the tools, commands and menu set the running process's env, so two pi
windows on one machine keep separate identities and can never overwrite
each other (a persisted identity in the shared config.json used to let one
window clobber the other's). Identity resets when the process exits
(re-set it, or launch with the env vars pre-set). The shared chat FILE
still resolves: `AFTC_CHAT_FILE` -> default log
`<dataDir>/chat/chat.log` (`getChatLogFile()` in paths.ts — the same
cross-platform pattern as aftc-codex's `<dataDir>/aftc-codex`). The chat
dir doubles as shared scratch space for future agent-to-agent file
exchange.

## Record format (chat.log, append-only)

```
[aftc_to:bob][aftc_from:alice][aftc_id:8f3a21c4][aftc_kind:message][aftc_message]
<multi-line content — code, PowerShell, anything — never regex-matched>
[/aftc_message]
```

- `aftc_kind`: `message` (default) | `done` | `claim`. `aftc_to:all` broadcasts.
- Optional `aftc_auto:1` token (after `aftc_kind`) marks an auto-reply
  engine record (loop guard, see below); old records parse as `auto: false`.
- Parser: header line tokenized `[aftc_key:value]` — content is opaque until
  a lone `[/aftc_message]` line; records separated by a blank line; offset =
  end of the last COMPLETE record (a truncated tail is re-read). A trailing
  newline's phantom split element is excluded so the next record's header is
  never skipped.
- Cross-platform: LF-only writes; CRLF + UTF-8 BOM stripped on read; Windows
  EBUSY/EPERM append retries; names sanitized (no brackets / CR / LF /
  control chars); content never passes through a shell.
- Per-instance state rides NEXT to the log (`<log>.state-<name>.json`):
  resume line, dedup ids, last peer, seen-done map, last checked line — keyed
  by participant name so two instances sharing one log never race a shared
  state file. Clearing rotates the log to `<log>.bak-<timestamp>`, drops a
  timestamped `<log>.rotated` marker (running instances treat post-clear
  content as new) and removes the state files.

## Startup guard (an old conversation never resumes itself)

- **Stale clear:** at session start, a log untouched for over an hour is a
  finished conversation — rotate it away (backup kept). Repeated startups
  within the hour never touch an active log (fresh mtime).
- **Prune:** a fresher log is trimmed to the newest 6 records per sender
  (order kept); aborts on a concurrent append or mid-write tail.
- **History skip:** no saved read position for this name = never replay
  pre-existing records — the baseline snaps to the CURRENT end of the log
  (phantom split line excluded, or the baseline lands past the next
  header and skips it). Exceptions: the log was empty at session start
  (everything is new) or the rotation marker is at/after the session start
  (a clear happened during this session, so post-clear content delivers).

## Engine

- Watcher: `fs.watch` on the chat dir (filtered to chat.log) + a ~10s stat
  poll fallback; started `session_start`, torn down `session_shutdown`;
  in-flight guard; offset/rotation handling.
- Delivery is confirmed BEFORE a record id is marked processed: if
  `sendUserMessage` throws, the record stays unprocessed and the resume
  line stops at its header, so the next scan re-delivers it (no silent
  loss). Auto-reply owes EVERY addressed sender of a batch (recipient set,
  not a single slot).
- Injection: a record addressed to me (or `to:all`) with an unseen id →
  `pi.sendUserMessage("From <name> [chat]: …")`; `deliverAs` chosen from an
  `agentActive` flag (idle = immediate; streaming = `followUp`).
- Auto-reply (`chatAutoReplyEnabled`, default on): a message addressed to me
  is answered automatically — on `agent_settled` the assistant's final
  message is appended addressed to the sender, flagged `aftc_auto:1`.
  `to:all` messages are NEVER auto-replied; the user typing cancels a
  pending reply; `chat_done` cancels it too. An auto-sent reply is NOT a
  completion signal — completion requires `chat_done` (enforced in the
  injected rules block).
- **Loop guard:** an `aftc_auto:1` record is delivered tagged
  "(auto-reply)" but NEVER owed an auto-reply back — two AIs exchange at
  most ONE automatic round per human message.
- **NO_REPLY suppression:** when the model's whole reply starts with
  `NO_REPLY`, the auto-reply is swallowed (nothing is appended) — the
  sanctioned way to acknowledge silently; bare acks and small talk are
  banned by the rules block (every sent message costs allowance).
- **Done silencing:** after `chat_done` (`iAmDone`), done/claim notices
  are no longer injected (each injection costs a model turn); a real
  message addressed to me re-engages delivery.
- Chat rules block: injected into the system prompt while enabled
  (`before_agent_start`) — identity, addressing, auto-reply rules, the done
  protocol, and job coordination (first claim wins; assign by NAME from
  chat_status, never "whoever answers").

## Tools (always registered — chat is a permanent, always-on feature)

| Tool | Params | Notes |
| --- | --- | --- |
| `chat_set_name` | `name` | Sets this instance's chat name |
| `chat_set_role` | `role` | Sets this instance's role |
| `chat_send_message` | `recipient`, `message` | Sender always the saved name; requires name + role |
| `chat_status` | — | Name, role, file, watcher, participants, who's done, recent activity |
| `chat_done` | `note?` | Explicit completion notice to everyone (never silent stoppage) |
| `chat_claim` | `task` | Commit to a broadcast job — first claim in the log wins |
| `chat_clear` | — | Clear/rotate the shared log (destructive) |

All get `description` + `promptSnippet` + `promptGuidelines` naming the tool
explicitly. When disabled, the tools are absent (zero prompt cost) and the
on/off commands still work.

## Commands

- `/chat` — options menu ONLY (no arguments; sending is `/chat-to` or the AI)
- `/chat-set` — guided identity setup: "What is this AI's name?" then
  "What is this AI's role?" via two native `ctx.ui.input` prompts (pi's
  input has no length cap; over-long answers truncate to 24 with a notice)
- `/chat-to <name> <message>` — send to a named peer; multi-word recipients
  match against recent participants (longest name wins), else first word
- `/chat-set-name <name>` / `/chat-set-role <role>` — set this window's
  identity (per-process; never affects other windows, not persisted)
- `/chat-clear` — clear/rotate the log (confirm)
- `/chat-check` — new messages since your last check + who's done
- `/chat-status` — full state

There is NO on/off: chat is a permanent feature (user decision). The
watcher starts on every session start and the tools are always present.

### /chat menu (aftc-ui, /codex layout)

Title "Chat options", body "Please choose:" — BLANK line between header and
options, `labelWidth`-aligned (never pack the title onto the options).

1. Open chat log dir (explorer / open / xdg-open, detached)
2. Set your chat name
3. Set your role
4. Clear chat log

## Coordination protocol (rules block)

- Messages to me → auto-answered (flagged auto); `to:all` → injected, never
  auto-replied; auto peer replies → never auto-answered (loop guard).
- No bare acknowledgements / no small talk — reply `NO_REPLY` when there is
  nothing to add; status goes in `chat_done`'s note; consolidate messages
  (every send costs the user's allowance).
- Unsure about something a peer owns → ask that peer directly by name.
- Scope hard rule: do ONLY what your user asked; work that would touch
  features/files outside that scope stops, the detecting AI flags it, and
  the task owner's AI asks the user — all AIs pause until the answer.
- `chat_claim` COMMITS: check chat_status for an existing claim first; the
  first claim in the log wins; a later claimer stands down and verifies;
  claims are commitments, not offers.
- `chat_done` is the explicit stop signal — completion is never silent.
- Assign jobs by NAME from chat_status — never leave a job to whoever
  answers (prevents the "both say you do it, nobody does" deadlock).

## Delivery & failure modes

- Delivery: idle → `sendUserMessage` (new turn); busy → `deliverAs:
  "followUp"` (queued until the current turn finishes).
- Log missing/locked → read returns "" / append retries on EBUSY/EPERM.
- Model turn hang is external (provider); the watcher keeps polling and the
  next record is delivered once the agent settles.
