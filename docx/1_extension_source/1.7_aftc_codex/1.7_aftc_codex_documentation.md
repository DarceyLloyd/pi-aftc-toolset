## Purpose

An OPT-IN, self-educating knowledge base: injects the maintainer's unified
codex rules + thinking guidance + a generated resource list into the
model's system prompt, and gives the model a `codex_load` tool to fetch
topic docs on demand plus write tools to record durable lessons. OFF by
default; fail-soft everywhere; never destroys user data. Owns everything
under `extensions/aftc-toolset/aftc-codex/` (7 TS modules + `scripts/`).
The package ships ONLY the 3 fixed maintainer docs (rules / guidance /
markdown-guidance); the topic `resources/` tree is entirely USER-generated
with the codex entry tools and is never touched by the extension's update
logic.

## Coordinator pattern

`aftc-codex.ts` owns the shared closure state (`CodexState`: `prepped`,
`silent`, `rulesOnly`, `noticedThisSession`) and wires the sub-modules;
sub-modules import shared types FROM it (type-only) and never import each
other. One `createAftcCodex(pi)` line in index.ts.

| Sub-module | Role |
| --- | --- |
| codex-store.ts | data-dir layout, fixed-doc seeding, resource reads (flat + nested + root-level), resource-list script spawn |
| codex-inject.ts | before_agent_start injection, session lifecycle, marker, rules-only mode |
| codex-commands.ts | the /aftc-codex-* command + menu surface |
| codex-detect.ts | project technology auto-detection |
| codex-learn.ts | /aftc-codex-learn instruction prompt |
| codex-entries.ts | codex_add_entry / codex_edit_entry / codex_remove_entry tools |
| codex-intent.ts | planning/documentation intent suggestion |

## Data layout (live vs seed)

- SHIPPED SEED (source only, replaced on pi update):
  `<packageRoot>/extensions/aftc-toolset/data/aftc-codex/` —
  `codex-rules.md`, `thought-and-action-guidance.md`,
  `markdown-guidance.md`. No topic resources ship.
- USER LIVE COPY (per-user): `<dataDir>/aftc-codex/` — the 3 fixed docs
  (copied from the seed, refreshed on package-version change) plus
  `resources/` (entirely user-generated via the entry tools).
- Version: `aftcCodexInstalledVersion` records the package.json version the
  fixed docs were last copied from. On startup, a mismatch re-copies the 3
  fixed docs and stamps the new version. User resources and the SQLite DB
  are never touched.

## Codex resource tree

The `resources/` tree starts EMPTY and is built entirely by the user. The
known category folders (created on demand by the entry tools):
languages, libraries, frameworks, engines, runtimes, tools,
servers-and-containers, database, os, file-formats, ui-ux (ui-ux nests by
platform: web/, desktop/, mobile/, plugin/; file-formats nests by format
family: audio/). Any extra folder is discovered dynamically.

```
resources/
├── codex-resource-list.md   # AUTO-GENERATED by sync-codex-resources.mjs
├── <root-level topics>      # user-created (eg documentation-and-planning)
└── <category folders>       # user-created topic docs (flat or nested)
```

## Lifecycle (normative)

1. Enable (`aftcCodexEnabled`) → first enable copies the 3 shipped fixed
   docs into the live codex and stamps `aftcCodexInstalledVersion`.
2. Fixed-doc refresh: once per extension load on the FIRST session_start, if
   the recorded installed version differs from `package.json`, the 3 fixed
   docs are re-copied and the version stamped. User resources and the SQLite
   DB are never touched.
3. `/codex-init` preps the session (inject + detect + fetch relevant
   docs); `/codex-refresh` strips and re-inits; `/codex-disable` strips
   from context; `/codex-inject-rules` = session-only rules-only mode
   (works even when disabled; cleared by /new).
4. Users build their own resources with `codex_add_entry` /
   `/codex-learn`; `/codex-install` / Start Fresh wipe the whole codex and
   restore just the shipped basics (explicit, confirmed).
