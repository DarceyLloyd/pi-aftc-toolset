## Function

Fixture PROJECTS used by `tests/docx/docx-check.mjs` (120 s) to verify the
/docx generator (1.8) against realistic inputs — they are test fixtures,
NOT sub-projects of pi-aftc-toolset, and they are deliberately varied to
exercise every project-type pack and the audit rules.

## Inventory

| Fixture | Shape (what it exercises) |
| --- | --- |
| `AFTC TS MVC WebGPU Template` | TS + webpack/vite + Three.js/GSAP web template (`basic-website` / `webgpu-webgl` packs) |
| `AFTC Voice to CLI (Electron App)` | Electron + node-pty + xterm + bundled CPython + local models (`desktop-app` pack) |
| `AFTS - Plug n Play (Java App)` | Maven Java app with HTML screens + a .NET DragTester side tool (`desktop-app`/`generic`) |
| `Docker Web Project` | Container-heavy stack: compose services `mysql-aftt`, `phpmyadmin-aftt`, `phpapache-aftt`, a PHP MVC framework, Admin + Public frontends (`web-app` pack; container mapping rules) |
| `Inversionator C++ VST` | JUCE/CMake C++ audio plugin + third_party JUCE + clap extensions (`juce-vst` pack; vendored-tree exclusion) |
| `docx_test_01` … `docx_test_08` (+ `_badtype`, `_detect`, `_gate`, `_nodetect` variants) | Minimal shapes: first-run, re-run fold-in, docs/ leftovers, nested ID trees, orphan surfaces, detection/gating behaviour |

## Fixture rules

- The docx test is NEVER run unprompted (ask the user first — AGENTS.md).
- Fixtures are read by the test harness; their contents (including the
  compose files, package manifests and html screens) exist to be scanned
  by map-scan/ui-hints — the audit asserts hint coverage on them.
- They contain their own `docx/` outputs from previous test runs; those
  are fixture data, not documentation of this project.
